# TRD-2026-4dec59b8: Local-CI PR Approval

Based on PRD: docs/PRD/PRD-2026-4dec59b8-local-ci-pr-approval.md (v1.0.5, Locked)

## Architecture Decision

**Chosen approach (Option C):** A `local-ci-gate` skill owns the editable procedure; a small set of pure-JS helpers in `packages/development/lib/` owns only what must be unforgeable; `pr-merge.yaml` invokes the skill.

- `packages/development/skills/local-ci-gate/SKILL.md` is the single reusable procedure and owns everything a maintainer would plausibly tune (Constitution Rule 8): the order of the run, the messages, the bead wording, and how failures are explained.
- Pure-JS modules in `packages/development/lib/` own only what grades a claim or protects a boundary (Rules 7 and 8's enforcement exception): run-record verification, bot-vs-human classification, bead dedupe keys, approval-set config validation, and status publishing through `gh`. They make no network calls except the one module whose purpose is to post a status.
- `packages/git/commands/pr-merge.yaml` calls the skill at its existing Merge phase. It does not restate gate logic.
- The gate runs in-session in the maintainer's own process. There is no daemon, scheduler or background sweep (Rule 4; REQ-012).

**Alternatives considered (user chose C):**

- **Option A -- prose-only:** fewest files, but head-binding, run-record verification and human/bot classification would be prose a model can misread, and tests could only assert wording. Rejected: the PRD's core property is that evidence cannot be reused across commits.
- **Option B -- TypeScript runtime in agent-core:** strongest typing, but adds a build/dist surface and pulls editable criteria toward code against Rule 8. Rejected: the one place a real client is tempting (posting a status) is a single `gh api` call.

**Dependency decision (user approved):** no new dependency. The status is posted by calling the maintainer's own `gh` CLI with an argv array (never a shell string), so there is no HTTP client, no JWT signing and no key handling. **Trust decision (user, 2026-10-22): no GitHub App; trust is honest-actor** (see Security design).

**Rationale:** Option C matches repository precedent (TRD-2026-82b6a138), keeps editable behavior out of TypeScript, and is the minimum code that makes the trust properties testable.

## System Architecture

### Components and boundaries

1. **`SKILL.md` (local-ci-gate)** -- orchestrates a gate run: resolves the PR, fetches the head SHA, delegates the clean clone and CI execution to the runner, calls the CLI to build and verify the run record, publishes the status, and reports. The only component that talks to `git` and `gh`.
2. **`local-ci-config.js`** -- validates the per-repository config (approval set, excluded jobs, status context name, bot-review handling, tracker). Fails closed on unknown or missing fields (AC-017-3).
3. **`local-ci-record.js`** -- builds and parses the run record carried in the status description (CI tool version, workflow-set hash, log digest) and verifies it against the PR head and configured set (AC-004-5, AC-004-6, AC-003-1/2).
4. **`local-ci-status.js`** -- the only network module: posts the commit status by calling `gh api repos/<owner>/<repo>/statuses/<sha>` with an argv array (never a shell string). Refuses to attest when there is no `gh` login or the post fails, redacts secrets, caps the description at 100 characters, and never reads, logs or stores the `gh` token (REQ-004, REQ-010).
5. **`local-ci-review.js`** -- classifies review authors by GitHub account `type` (Bot vs User), never by name, and decides whether a review set blocks (AC-006-3, AC-006-4).
6. **`local-ci-sweep.js`** -- given fetched facts about recently merged PRs, returns the bot findings and hosted-CI failures not yet tracked, using stable dedupe keys (AC-007-2, AC-008-3).
7. **`local-ci-cli.js`** -- JSON-in/JSON-out entry point wrapping the modules above, with boundary validation (Constitution Rule 2). Added to `lib-bundler.ts` `ENTRY_FILES` so Pi installs ship it.
8. **`pr-merge.yaml`** -- calls the skill in its Merge phase, replaces the `CHANGES_REQUESTED`/required-check refusal with the gate's verdict, and runs the sweep.

### Data flow

```
pr-merge -> local-ci-gate skill
  1. gh: PR head SHA, base, reviews   -> local-ci-cli review   (classify bot vs human; human CHANGES_REQUESTED blocks)
  2. git clone <tmp> @ <headSha>      -> the TRUSTED command list (from the base ref) run by the runner in <tmp>, once per required Node version; PASS/FAIL = exit status the runner observes
  3. step results + digest            -> local-ci-cli record   (build run record)
  4. record                           -> local-ci-status post  (gh api: POST status on headSha, maintainer's own gh login)
  5. gh: read status back             -> local-ci-cli verify   (record matches head + configured set)
  6. verified + no human block        -> gh pr merge
  7. post-merge                       -> local-ci-cli sweep    (open beads for new bot findings / CI failures)
```

### Integration points and failure handling

- **Status publish fails or no `gh` login:** the run may complete but publishes nothing and reports it cannot attest (AC-004-7); the merge is refused.
- **Prerequisite missing (git, Node, or the repository's CI entry point):** stop before any status is posted, naming the missing prerequisite (AC-015-2).
- **Head commit cannot be fetched:** stop, publish nothing (AC-003-4).
- **Verification mismatch (head or workflow set differs):** refuse the merge and print the mismatch (AC-004-6).
- **Unmirrored or unrunnable step:** a required workflow step that the configured step list does not mirror, or a required Node version that cannot be provided, fails the gate and names the step or version (AC-009-2).

### Security design

- The maintainer's `gh` token is never read, printed or stored by the gate: it stays inside `gh`, is not passed to CI steps, and `redact()` is applied to every string the CLI emits and strips token-shaped values and the values of `GH_TOKEN`/`GITHUB_TOKEN` (AC-010-2).
- **Trust model: honest-actor, stated plainly.** Branch protection may require the check `ensemble/local-ci` by name, unpinned (`app_id` null on read, written as `-1`, meaning any source). The verifier does not check who created a status (AC-004-4): a status for the configured context from any identity is accepted if its run record verifies against the PR head SHA, the workflow-set hash, the runner blob hash and the config blob hash. Anyone with write access can therefore forge a status; the gate prevents accidents and agents merging unverified work, not deliberate forgery. A pinned GitHub App could close this later and is out of scope.
- Review text and comment bodies are untrusted: only structured fields (author type, state, commit, thread resolved flag) are read for classification; bodies are passed to beads as quoted data, never interpreted.
- **Known limit (accepted in the PRD):** nothing proves the CI steps actually ran; the run record makes careless or stale posts detectable, not impossible.

### Hosted-result reuse (TRD-015, REQ-019)

Design as built. The local run is the approval signal; this section lets results hosted CI already produced for the same head stand in for it when, and only when, they can be verified from GitHub and the base ref without believing anything the PR head supplies.

- **Module and call sites.** `packages/development/lib/local-ci-hosted.js` exports `verifyHosted({repo, headSha, baseSha, repoRoot, approvalSet}, deps)`, pure over injected `deps` (`git`, and `ghApi(path)` returning `{ok, json | error}`). It runs nothing and posts nothing. The CLI queries GitHub itself; the payload never carries hosted data.
- **Opt-in: `hosted_reuse` in `.ensemble/local-ci.yaml`,** read from the base ref only (like every other key). `covers` lists the local step names hosted CI runs; `extra_workflows` lists `{file, jobs: [{id, matrix}]}` for hosted jobs outside the default approval set (here `generated-drift.yml`, job `drift`). `local-ci-config.js` turns it into `approvalSet.hostedReuse = {covers, checks}` or `null`. **Every name in `steps` must appear in `covers`**; otherwise the config does not validate for reuse and reuse is off, so adding a local step without declaring a hosted counterpart fails safe. Absent key: behaviour is unchanged.
- **Required job names are derived,** never read from the head: from the approval-set checks plus `extra_workflows`, as `<id>` or `<id> (<matrix values in key order>)` (for this repository `validate`, `test (22)`, `test (24)`, `drift`). If the base-ref workflow file gives the job a custom `name:`, it is used only when it is a plain literal (no `${{`) and the job has no matrix; any other custom name, or a job missing from the base workflow, refuses.
- **Workflow-file equality.** The git blob of each required workflow file at the PR head (`git rev-parse head:path`) must equal its blob at the base ref. Hosted CI executes the head's workflow, so a head that edited it could make `validate` pass trivially; with identical blobs the hosted command list is the one the base config was reviewed against. A PR that touches such a file is refused for reuse and graded locally, the same principle as base-ref config grading (the change applies after it merges).
- **Source of truth: the Actions API, not checks or statuses.** The CLI reads `GET repos/<repo>/actions/runs?head_sha=<head>` and `GET repos/<repo>/actions/runs/<id>/jobs`. Check runs and commit statuses are deliberately not used: a commit status is postable by anyone with write access, and a workflow holding `checks: write` can create a check run under the GitHub Actions app (app id 15368; per GitHub documentation, not probed here), so a name and app-id match would let a head-supplied workflow forge `validate`. Branch protection itself matches name and app id; this gate is stricter than that.
- **Run and job selection.** A run counts only if it has an integer `id`, its `head_sha` equals the head, its `path` is the configured workflow file, its event is `pull_request` or `push`, it is bound to this PR (next bullet), and it is completed. Per (workflow file, event) only the latest run counts, so a re-run that went green replaces a red one and a later red replaces an earlier green. A `pull_request` run per workflow is required. Each required job must be present with the derived name, on the head, completed, with conclusion `success`. Missing, failed, cancelled, skipped, running, or truncated listings (more runs or jobs than were read) refuse.
- **Binding to the PR.** Only runs whose `pull_requests[]` contains THIS PR's number with `base.ref` equal to the PR's base branch are considered. Any other run (another PR sharing the head SHA, another base branch, an empty `pull_requests` such as a fork-PR run or a closed PR) is ignored: it cannot count and cannot mask or replace this PR's run. A fork PR therefore never gets hosted acceptance (fail closed: the gate runs locally). The run's `base.sha` is NOT compared: `dev` moves constantly and equality would switch reuse off.
- **Shape fails closed.** If ANY run bound to this PR for a required workflow file, on the head, with an event in `pull_request`/`push`, has a non-integer `id`, reuse is refused naming the file and the id (the run is never dropped silently; runs not bound to this PR are ignored whatever their id). Both Actions listings (runs and jobs) must carry an integer `total_count`, else refuse; every required job must have been matched for the `pull_request` event. The result is never `ok` with an empty or short job list. The last check, that every required job was verified in a `pull_request` run, is unreachable by construction and is kept as an assertion that throws (`verifyHosted: internal error: ...`, a programming error, never a refusal).
- **Repo-local actions.** Hosted acceptance is refused, with a named reason, when a required job of a required base-ref workflow uses a repo-local action or reusable workflow (a `uses:` starting with `./`, at job or step level): the PR can change those files while the workflow file stays identical. The same refusal applies to every job in the `needs:` closure of a required job (transitive, same workflow file, cycles safe). Also refused, in a required job or its needs closure, at job or step level: `continue-on-error` with any value other than the literal boolean `false`, and an `if:` whose text matches `github\.(head_ref|actor|triggering_actor|event)\b` (`PR_CONTROLLED_IF`): that is `github.head_ref`, `github.actor`, `github.triggering_actor`, `github.event` and every `github.event.<anything>`, while `github.event_name` is NOT matched (the `\b` does not split `event_name`; the trigger fixes it and the PR does not control it). PR-controlled context can skip a step while the workflow file stays byte-identical. These are structural checks and a blacklist of PR-controlled contexts, not a proof; expressions outside that list, matrix or env values, external actions pinned by tag and reusable workflows from other repos stay unverified. External actions (`owner/repo@tag`) are trusted as pinned by tag, not by SHA.
- **Merge ordering (`merge`).** `merge` keeps its payload shape; `statuses` is still the transport of descriptions and SHAs for record verification. LOCAL route: when a payload status verifies, `merge` first calls the one verdict function (bullet "Local failure veto: one rule"); a veto refuses (`<reason>; re-run the gate with forceLocal:true`, `localFailure` when something is recorded, no `hostedRefused`), while `verified` or `none` accepts: a newer `failure`, `pending` or unverified success on GitHub beats an older verified success in the payload, a verified GitHub success supersedes the payload, and when GitHub lists nothing in the context (`none`) the payload's verified success is accepted. The payload's own non-success statuses in the configured context are then judged by the same helper (`payloadVeto`) as on the hosted route, so a verified success listed first no longer hides a later adverse entry; a veto from it refuses in the local-route shape (`localFailure`, no `hostedRefused`). HOSTED route: after `verifyHosted` succeeds and before the PR re-read, ONE verdict call (at most one statuses read per merge); a veto refuses with `<local reason>; hosted CI is green on this head but is not accepted: <veto reason>; re-run the gate with forceLocal:true`, `hostedRefused:true`, and `localFailure:true` only when something other than a verified success is recorded. The caller's own payload counts only against the caller (`payloadVeto`, both routes): a configured-context payload status whose state is not `success` (failure, error, pending, any other or non-text state) vetoes when its `sha` is not a usable full commit SHA (it cannot be attributed to another commit, so GitHub's answer cannot clear it), and vetoes when its `sha` is the head and GitHub lists nothing in the context; when GitHub's latest is a verified success that success is newer than the caller's evidence and the payload status on the head does not veto; a payload status on another full SHA never vetoes. Otherwise `merge` re-reads the PR (`gh pr view`) and refuses if it is no longer OPEN or its head changed; if unchanged, the result is `mergeReady:true, source:'hosted', hostedJobs`. If hosted is not accepted the merge is refused and the reason appends the hosted reason to the local one. The verified SHA is NOT passed to the merge step (`--match-head-commit`): `pr-merge.yaml` is at 2499 of its 2500-word ceiling. Human `CHANGES_REQUESTED` still blocks as before.
- **Gate ordering (`gate`).** After the PR and config checks: the hosted shortcut (skipped by `forceLocal`); after `verifyHosted` succeeds, the same verdict function; a veto skips the shortcut and runs locally with `hostedRefused` set to `hosted CI not accepted: <reason>`; `verified` or `none` leads to the PR re-read (`gh pr view`): if no longer OPEN or its head changed, `gate` stops at stage `config`, exactly like the first identity check, and does not fall back to a local run; if unchanged it returns `{stage:'hosted', ok:true, mergeReady:true, source:'hosted', hostedJobs, ranLocally:false}` with no lock taken, no run and no post (the check only reads GitHub, so it never queues behind a running gate). Missing, red, pending, vetoed or unverifiable hosted results fall through to the local run, which takes the lock (`local-ci-lock.js`) like any other run, posts the write-ahead `pending` (next bullet), runs, records. Payload key `forceLocal:true` (boolean) skips the shortcut.
- **Write-ahead pending.** A non-dry `gate` that runs locally posts `pending` in the configured context on the exact head, with description `ci-local running @ <sha8>`, INSIDE the lock callback (a lock refusal posts nothing) and immediately before the runner. If the post does not return `published:true` (any error, 403, rate limit, no publisher, a throw) the gate REFUSES to run: `stage:'pending'`, `error` beginning `cannot record that a local run is starting`, `ok:false`, `mergeReady:false`, `posted:false`, nothing cloned, nothing else posted. After the run, a pass posts `success`; a not-passed run posts ONE `failure` for its first head-bound failure; a transient-only refusal posts nothing and LEAVES the pending, which keeps vetoing (availability over safety, on purpose); a thrown runner becomes a head-bound `runner-error` failure and is posted; every final post is wrapped so a throwing publisher becomes `published:false`, and when the final post does not publish the pending remains (`pendingRemains:true`, said in `error`). A crash, kill, timeout or failed final post therefore leaves the LATEST status `pending`, which vetoes. Dry runs and the `run` command never publish, so their outcome never vetoes. The gate needs permission to post statuses before the run as well as after it. It does not clear a veto by itself: only a later passing local run posts a verified `success`, whether it is a `forceLocal:true` run or a non-forced `gate` whose vetoed hosted check fell through to the local run.
- **Local failure veto: one rule.** One function, `localRunVerdict`, read from GitHub by both `merge` and `gate` only after `verifyHosted` returned ok: `GET repos/<repo>/commits/<head>/statuses?per_page=100`, newest first; the FIRST entry whose `context` equals the configured context (case-insensitive) decides. The configured context is the `status_context` of the BASE config of the PR's base branch (`ensemble/local-ci` in every repository surveyed); a base config that names another context moves the veto with it, because the gate posts to the same configured context. It returns `none` (readable, well formed, shorter than a full page, nothing in the context: nothing local ever ran), `verified` (the latest is a `success` whose description passes `verifyRecord` for this head) or `veto`. Veto, fail closed: no `ghApi` or an unreadable or non-array answer; an entry that is not an object or has no string `context`; entries in the context whose integer `id`s show the list is not newest first; a full page of 100 with no entry in the context (it may lie beyond the first page); a latest `success` whose record does not verify; a latest `pending` (a local run did not finish: it is running or it died); a latest `failure`, `error` or any other or non-text state. `verifyRecord` binds the commit, the trusted config blob, the workflow-set hash and the record format; it does NOT bind who posted the status, so anyone with write access can post a verifying success (honest-actor model, AC-004-4, stated plainly); the local success route has the same property, so hosted reuse is no weaker than what the gate already trusts. `merge` refuses (`forceLocal:true` advised); `gate` falls through to the local run. A veto clears when any local `gate` run passes and posts a verified `success`, which is then the latest: a `forceLocal:true` run, or a non-forced `gate` whose vetoed hosted check fell through to the local run (`forceLocal` only skips the hosted check); a bare or unverifiable success never clears.
- **Head-bound vs transient refusals.** A local run that fails publishes a `failure` commit status for the head, replacing the write-ahead `pending`, and so vetoes, when the failure is head-bound: `step-failed`, `unsupported-step`, `clone-tampered`, `unexpected-output`, `unreadable-workflow`, `clone-moved`, `clone-config-changed`, `runner-error` and any unknown or future kind (the description is `ci-local failed: <workflow> / <job> / <step> @ <sha8>` for the first two, `ci-local refused (<kind>): <job / step parts, or clean clone> @ <sha8>` for the rest). Transient kinds (`invalid-input`, `prerequisite`, `secrets`, `cleanup`, `unfetchable-head`, `node-version`: the head was never evaluated) publish NOTHING and LEAVE THE PENDING, so they keep vetoing until a later local run passes (availability over safety, stated). One status is posted for the first head-bound failure; dry runs never publish; a refusal listing no failures publishes nothing and leaves the pending; if the publisher cannot post the final status the pending remains (`posted:false`, `pendingRemains:true`). An infrastructure error that published a failure (`runner-error`) clears the same way, with a later passing local run.
- **Runner cleanup never throws over a result.** A step can leave unreadable directories. `removeTree` removes with `force` and retries, repairs permissions (directories only, never through a symlink) and retries once, and returns the error instead of throwing. Cleanup runs after the body has produced its result and is merged into it: a clone that cannot be removed is a head-bound `runner-error` failure (`could not remove the clean clone <dir>: ...`), even if every step passed, so it is published and vetoes; scratch-HOME problems are folded in the same way; `keep` is unchanged; the stale-clone sweep uses the same function and still throws (the transient `cleanup` kind). The untracked-file check fails closed too: git exits 0 with a `could not open directory` warning for a directory a step made unreadable and lists nothing inside it, so `untrackedFiles` returns null on that warning (before the first step and after every step) and the run is `clone-tampered` ("could not inspect the clone"), not a pass.
- **Isolation of the PR head's steps from the gate's credential.** The steps run the PR head's own code as the maintainer, so a head step could post a verifying `success` with the maintainer's credential and clear the veto. The runner therefore withholds what it can. Per run it creates one scratch directory (mode 0700) and points `HOME`, `GH_CONFIG_DIR`, `XDG_CONFIG_HOME`, `XDG_CACHE_HOME`, `XDG_DATA_HOME`, `XDG_STATE_HOME` and `TMPDIR` into it; sets `GIT_CONFIG_GLOBAL` and `GIT_CONFIG_SYSTEM` to the null device, `GIT_CONFIG_NOSYSTEM=1`, `GIT_TERMINAL_PROMPT=0`, `GH_PROMPT_DISABLED=1`, `GH_NO_UPDATE_NOTIFIER=1`; and adds `ENSEMBLE_LOCAL_CI_RUN`, a fresh random id per run. The rest of the environment is the allowlist (`USER`, `LOGNAME`, `SHELL`, `LANG`, `LC_ALL`, `TERM`, `NODE_OPTIONS`), `CI=true`, `npm_config_cache` (warm installs) and the secrets the config names (the maintainer's explicit choice); `GH_TOKEN`, `GITHUB_TOKEN`, `GH_ENTERPRISE_TOKEN`, `GITHUB_ENTERPRISE_TOKEN`, `GITLAB_TOKEN`, `NPM_TOKEN`, `NODE_AUTH_TOKEN`, `SSH_AUTH_SOCK`, `GIT_ASKPASS`, `SSH_ASKPASS`, `GH_HOST`, the maintainer's `GH_CONFIG_DIR` and `XDG_*`, `AWS_*` and every other variable are never forwarded. `PATH` is `<binDir>`, then a scratch directory holding one `gh` stub (a message on stderr that the gate does not give the PR head's code its GitHub credential, exit 127), then the maintainer's `PATH` unchanged: the toolchain stays reachable, and dropping entries would gain nothing because an absolute path still works. After the LAST step, on every path that returns a result after a step process was started, before the clone is removed and before `gate` posts its final status, the runner SIGKILLs the process group of every step process that still had a member and sweeps the current user's processes whose environment carries the run's `ENSEMBLE_LOCAL_CI_RUN=<id>` token (Linux: `/proc/<pid>/environ`; macOS: `ps -axww -E`, which does not show the environment of Apple's own binaries such as `/bin/sh`, `/bin/sleep` or `/usr/bin/perl`; other platforms: no sweep), never its own pid or its parent, matching the whole token; it reports `leftoverProcessesKilled` only when it killed something, which changes no verdict. A step that exits normally keeps its daemons until the end of the run, so cross-step daemons keep working. The runner's own git, clone and fetch commands keep the maintainer's environment. **Closed:** inherited tokens and `GH_*`, `XDG_*` and `HOME`, git global and system config, a bare `gh`, and leftover process groups and marker-carrying processes at the end of the run. **NOT closed** (head code runs as the same OS user): real credential files reached by absolute path or through `os.userInfo().homedir`, the macOS keychain through `security` or `git-credential-osxkeychain`, any other credential store the maintainer holds, a child that scrubs its environment AND leaves the process group (on macOS also one that left the group under an Apple binary), and a workflow that holds `statuses: write`. HOME redirection is not a sandbox. **Not done, as options:** `sandbox-exec` on macOS, `bwrap` or `unshare` on Linux, steps under another OS user or in a container, a status-posting identity the steps can never reach.
- **Needs closure and step conclusions (`verifyHosted`).** Every job in the `needs:` closure of a required job that is not itself required must be present in the same run, completed, on the head, with conclusion `success` (a closure job with a matrix, a custom or computed name, or no definition refuses before any GitHub call); they appear in `hostedJobs` with `needed:true`, so a required job with `if: always()` whose needed job failed is refused. Every REQUIRED job's `steps` listing must hold integer `number`, string `name`, `status` and `conclusion`, begin with `Set up job` and end with `Complete job` (GitHub's own, exempt); the next `n` entries (n = the base workflow job's step count, mapped by order because real listings have a numbering gap) are the workflow's steps and each must have concluded `success` (a `skipped` step is accepted only where the base step's `if:` is a pure matrix comparison, for example `Upload coverage` on `test (22)`); anything after them must be a completed `Post ...` step with conclusion `success`. This step check is the REAL guard; the earlier `if:`, `continue-on-error` and repo-local `uses` refusals stay as early static refusals (a blacklist, not a proof).
- **Refusal reasons** all read `hosted CI not accepted: <reason>`: reuse not enabled; no GitHub lookup; head or base not a full SHA; no hosted jobs named; workflow file missing at base or different at the head; unreadable or invalid base workflow; job not defined; custom or computed job name; required job or a job in its `needs:` closure uses a repo-local action or reusable workflow; `continue-on-error` other than `false`, or an `if:` matching `github\.(head_ref|actor|triggering_actor|event)\b` (`github.head_ref`, `github.actor`, `github.triggering_actor`, `github.event` and `github.event.<anything>`, not `github.event_name`), in a required job or its needs closure; a run bound to this PR with a non-integer id; runs or jobs unreadable, truncated or without an integer `total_count`; no `pull_request` run bound to this PR (number and base branch) with an integer id; latest run or job not completed; required job missing or not matched for the `pull_request` event; job not on the head; job concluded other than `success`; the latest status in the configured context on the head is not a verified success (`pending`, `failure`, `error`, an unexpected state, an unverified success), the statuses are unreadable, not a list or not newest first, or a full page of 100 has no status in the context (the veto, read by `merge` and `gate`; `merge` refuses, `gate` runs locally instead); a configured-context payload status that is not `success` with no usable `sha` or, when GitHub lists nothing, on the head (`merge`, hosted and local route alike); a job in a required job's `needs:` closure with a matrix, computed name or no definition, absent, or not concluded `success`; a required job whose steps are missing, malformed, out of the positional mapping, or not all concluded `success`; PR no longer OPEN or head changed after verification (`merge` refuses; `gate` stops at stage `config`).
- **Trust: what is verified.** The Actions service created these jobs (users cannot post Actions job objects), for the exact head SHA, in a run bound to this PR's number and base branch, from the named workflow path, under the derived names, and the workflow file equals the base's.
- **Trust: what is NOT verified or claimed.** Who triggered the run or posted anything; that the workflow's steps are honest beyond file equality (package scripts are head code, as in the local gate, which also runs head code); that the merge commit a `pull_request` run tested (head plus the base tip at run time) is the base tip as it is now (the run IS bound to this PR's number and base branch, but its `base.sha` is not compared because `dev` moves constantly); that external actions (`owner/repo@tag`) are what they were when reviewed, since they are trusted as pinned by tag, not by SHA; that the verified SHA is the one that is merged, since it is not passed to the merge step (`--match-head-commit`, see `pr-merge.yaml` ceiling above) and the PR is only re-read once after verification; fidelity of hosted `validate` and `drift`, which run on Node 24 only where the local gate runs both 22 and 24 (accepted and declared in the config comment); and `generate-validate` (`npm run generate:validate`) is not a hosted step, so the config declares it covered by `npm run generate`, which hosted `validate` and `drift` both run and which validates the same YAML. Residuals, stated plainly: a status writer with the gate's credentials can post a verifying success and so clear a veto, and so can the PR head's own steps, which run as the maintainer (the isolation bullet above lists what it closes and what it does not; HOME redirection is not a sandbox); the window between the statuses read and the actual merge (TOCTOU) is open; a dead gate leaves `pending` and the precheck does not start a gate while any status in the context exists, so recovery is a manual `gate` run; expressions outside the `if:` whitelist are refused rather than evaluated; steps inside composite actions are not listed by the API and the step-name mapping is positional; external actions are pinned by tag; `base.sha` is not compared. To refuse reuse for any of these, delete the name from `covers`.
- **Rejected options.** (1, literal) Match check names from the checks API with nothing else: loses *no trust in the PR head*, since the name and app can be produced by a head-supplied workflow and a head can rewrite the workflow that produces the green, and it ignores steps hosted does not run. (2) `pr-merge.yaml` skips the gate when hosted is green: loses the CLI-computed verdict, base-ref grading and testability, because the decision would sit in prompt prose where nothing refuses a moved head, a red job or a config mismatch. (3) The local gate only as an opt-in fallback: leaves every PR paying the duplicate run by default; kept only as the fallback path and as `forceLocal`.
- **Non-goal.** No branch-protection call exists anywhere in this design, in code or in skills.

### Key risk, stated openly

The design rests on honest-actor trust, not on a forge-resistant mechanism (see Security design). One factual dependency is not yet observed: that an unpinned required check named `ensemble/local-ci` is satisfied by a commit status posted with `gh` on a real protected branch. TRD-010's runbook records that observation on the real repository (first real success status, then the requirement, then a PR seen blocked without the status and mergeable with it) and restores the pre-change snapshot if it does not hold.

## Architecture Self-Critique

1. **Gap, trust and sequencing (resolved by user decision, 1.0.12):** earlier versions required a maintainer-owned GitHub App, a live proof (TRD-001) that an App-posted status satisfies an App-pinned check, and an App client (TRD-004). The user removed the App because creating, installing and holding a key for it was a barrier to entry. The status is now posted with the maintainer's own `gh` login (TRD-014), the required check is unpinned, and trust is honest-actor: any identity with write access can post a status, and the gate accepts it only if the run record verifies. TRD-001, TRD-001-TEST, TRD-004 and TRD-004-TEST are deleted; the statements about them in 1.0.1, 1.0.6 and 1.0.8 are superseded. What stays unproven is that an unpinned required check is satisfied by a `gh` status on the real repository and the longest description GitHub accepts (TRD-014 enforces 100, below the working limit of 140); TRD-010's runbook observes the first at enablement.
2. **Gap, contradiction with an existing module:** `pr-review-remote.js` classifies bots by a configured login list, while PRD AC-006-4 requires classification by GitHub account type. Resolution: TRD-007 is a separate module that reads `type`; `pr-review-remote.js` is left untouched because `fix-issue` and `implement-trd-beads` still depend on its fail-closed behavior.
3. **Gap, tracker coupling:** The sweep creates beads through `br`, which exists in this repository but not necessarily in an adopting repository such as Foreman. Resolution: the tracker is a config field (TRD-002); the sweep returns structured items, and the skill hands them to whichever tracker the config names.
4. **Missing failure path:** if the status is posted but the PR head moves before the merge call, the merge could race. Resolution: the merge step re-reads the head SHA and re-verifies immediately before calling `gh pr merge` (TRD-005, TRD-009).
