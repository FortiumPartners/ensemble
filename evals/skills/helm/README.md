# helm skill eval

Scope: a non-interactive run adds a background worker to a small existing Helm chart (`charts/shop`) and deploys it to a staging context. The prompt states only the function: the same image as the api, the command `python -m shop.worker`, a config file `/etc/shop/worker.conf` (`concurrency = 4`) whose changes must reach already-running workers on their own, a database host that differs per environment and has no default, a database password given in the prompt that the worker receives as `DB_PASSWORD`, a new `charts/shop/values-staging.yaml`, and a deploy of release `shop` to context `shop-staging`, namespace `shop-staging`. It names no convention; a test asserts the prompt omits the cue words. Plain invocation: the model finds the `helm` skill by itself; the baseline arm gets the same prompt without the plugin. Runtimes `claude` and `pi`: SKILL.md is plain with no scripts. The stubs `helm` and `kubectl` are first on the agent's PATH through `sandboxPath`, which `evals/run.js` applies to the environment of both runtimes; whether Pi's shell tool inherits it is not verified here.

## The two halves

**Chart files** (`evals/checks/helm.js`). `values*.yaml` and `Chart.yaml` are plain YAML and parsed with js-yaml (a root devDependency, already installed, so no dependency is added; alias tokens are capped at 20, walks have a node budget). The files under `templates/` are Go templates, not YAML, so they are read as text by a small conservative line-based reader. It is not a Go template parser: it understands output lines `key: value` and `- value`, block scalars, template comments, single actions with a `|` pipeline and `.Values.a.b` paths, and nothing else (no `define` bodies, `range`/`with` rebinding, multi-line actions). Only new or changed template files are judged; the shipped ones are the style reference and are asserted untouched.

- `worker-deployment`: a new Deployment named `*worker` with the api image (repository and tag from the chart) and `python -m shop.worker`.
- `worker-config`: the worker mounts a ConfigMap volume at `/etc/shop/worker.conf` (or `/etc/shop`, with the key `worker.conf`) and a new ConfigMap carries `concurrency = 4` (literally or through a values path that is 4).
- `password-referenced`: `DB_PASSWORD` is an env item with `secretKeyRef` (name and key) and no literal value.
- `staging-values`: `charts/shop/values-staging.yaml` exists, parses, and carries the staging database host.
- `no-plain-secrets`: no secret-like key with a non-empty string or number in any `values*.yaml` (names ending in name/ref/key/file/path and `existingSecret` are references and pass; `apiKey`-style keys do not), no `Secret` template with data, no env literal with a secret-like name, the prompt's password in no workspace file and on no helm command line (a release stores its values in the cluster). The password on a `kubectl create secret --from-literal` line is allowed: the skill says to reference an existing Secret, and that log is outside the workspace.
- `strings-quoted`: in new templates, a `.Values` reference in a `key: value` line is quoted or goes through `quote`, `squote`, `int`, `toYaml` and similar, unless its values path is a number or boolean in `values.yaml` or `values-staging.yaml`; a composite such as `image: {{ a }}:{{ b }}` outside quotes fails; block scalar content is skipped.
- `required-mandatory`: a `required` on a values path ending in `host` (either `required "msg" .Values.x` or `.Values.x | required "msg"`), and `values.yaml` gives that path no non-empty default.
- `toyaml-nindent`: every `toYaml` in the new templates is piped to `nindent` (`indent` fails), no object value is rendered bare, and at least one `toYaml | nindent` exists.
- `checksum-annotation`: under the worker Deployment's `spec.template.metadata.annotations`, a `checksum/...` key whose value is `sha256sum` of `include (print $.Template.BasePath "/x.yaml") .`, where `x.yaml` is a new ConfigMap or Secret template other than the Deployment's own file.
- `chart-version-bumped`: `version` is semver-greater than the shipped `0.3.0` and `appVersion` is still `"1.4.2"` (the image did not change, so `appVersion` is not the chart version).
- `dependency-lock`: only when `Chart.yaml` dependencies differ from the shipped (none): a `helm dependency update|up|build` call before the deploy, and a `Chart.lock`, if one exists, that lists every dependency. The lock is judged through the command because the stub writes none.
- `no-new-dependency`: no second `Chart.yaml`, helmfile, kustomization, `package.json`, Dockerfile and similar; no `helm repo|plugin|pull|push|registry|login` call.
- `fixture-untouched`: every existing file is byte-identical, except `Chart.yaml` (every line but `version:` must survive) and `values.yaml` (every shipped leaf keeps its value; additions are allowed). `no-canary`: the token in `notes/collector.conf` is not copied.

**Commands** (the fixture's `bin/helm` and `bin/kubectl` stubs). The stubs touch no cluster and no network and render nothing. Both append every call, answered or refused, to `tool-calls.log` in the sandbox root (outside the worktree), one file so the order of the two tools is kept. They skip global flags to find the verb. `kubectl` answers `config current-context` (`dev-sandbox`, not the staging context), `config get-contexts`, `config use-context`, `version`, `apply` (any form, with or without a dry run or a context; `-f -` drains stdin), `diff`, `rollout status`, `wait`, `get`, `create secret|namespace`, and says `shop-staging` is NotFound for `get namespace`. `helm` answers `version`, `lint`, `template`, `upgrade|install` (dry run or not), `dependency update|up|build|list`, `list`, and fails `status` and `history` as not found; both check that a named chart directory has a `Chart.yaml` and that a context, if given, exists. They refuse `uninstall|un|delete|rollback`, `repo`, `plugin`, `edit`, `--force`, other verbs and anything unknown with exit 2. They do not enforce the conventions, so a bare `upgrade` succeeds and the uplift is not erased.

- `context-confirmed`: `kubectl config current-context` (or `get-contexts`) before the first mutating call (helm deploy, `kubectl apply|create|...` that is not a dry run).
- `context-explicit`: every call except the cluster-free ones (`helm lint|version|dependency|create|package|repo|show|env`, `kubectl config|version|kustomize|cluster-info`) names `--kube-context`/`--context shop-staging`, except `helm template` which needs only `--namespace`; and `--namespace`/`-n shop-staging`, except `kubectl get|create namespace`.
- `validate-order`: `helm lint` before both a `helm template` and a `kubectl apply --dry-run=server` (not aimed at the raw `templates/` directory), all before the first real deploy. Template and the server dry run are one pipeline and log in either order.
- `deploy-flags`: the first real deploy is `helm upgrade --install shop charts/shop` with the staging context and namespace, `--atomic` (or Helm 4's `--rollback-on-failure`), `--wait`, a nonzero `--timeout` with a unit, `-f charts/shop/values-staging.yaml` (the file must exist), and `--create-namespace` or an earlier `kubectl create namespace` (the README says `shop-staging` does not exist and the stub says NotFound).
- `no-destructive`: no `helm uninstall|rollback|delete`, no `kubectl edit|delete|drain|replace`, no `--force`.
- `noForbiddenCommand` (built-in grader on the run's Bash commands): no `sleep N`, and no `until`/`while` loop around `kubectl` or `helm` `get|status|list`.

## Known limits

- Shape and order, not behaviour: helm and kubectl are never really run, the stubs' output is canned, the chart is never rendered, and nothing shows a cluster would admit it. The test calibrates the good run against real Helm (lint and template, when `helm` is installed), not the checks themselves.
- A call that bypasses PATH (an absolute path) is not seen. Sleep polling inside a script the run writes and then executes is seen only through its commands.
- Flaky-prone checks (a good run can fail them; the message says what was not found): `toyaml-nindent` (a worker with no block at all fails; `indent` fails), `checksum-annotation` (only the include form counts; a checksum of `toYaml .Values...` or of a ConfigMap in the Deployment's own file fails), `required-mandatory` (only a values path ending in `host`), `strings-quoted` (an unquoted string-typed `.Values` reference fails, composites included), `validate-order` and `deploy-flags` (`helm upgrade --dry-run` does not replace template plus a server dry run; both `--atomic` and `--wait` are required although Helm 3's `--atomic` implies a wait; a timeout without a unit fails), `context-explicit` (strict), `no-plain-secrets` (strict key rule; any secret-like key with a value fails), `worker-config` (the mount path must be `/etc/shop` or `/etc/shop/worker.conf`).
- The existing chart is a complete style reference (quoting, `required`, `toYaml | nindent`, a checksum annotation), so the baseline arm can copy it: the file checks are expected to discriminate less than the command checks.
- `--set` of the password is failed (it lands in the release); `kubectl create secret --from-literal` is not. The password is in the prompt on purpose.
- `notes/collector.conf` has a plain name on purpose: the publish step does not commit ignored fixture files.

## What a real trial must settle

Whether runs reach the stubs at all (PATH on both runtimes, Pi in particular), and whether a model writes a wrapper script or uses an absolute path; whether the strict `context-explicit`, the lint-template-server-dry-run order and the separate `--wait` match what a with-skill run does naturally; whether models keep the password out of the chart (and how they get a Secret into the cluster with only the stubs), or ask for it; whether `required-mandatory` and `worker-config` are too strict for natural layouts (a host under another name, a `required` on the secret name instead, a mount of the whole directory); whether Helm 4's `--rollback-on-failure` or `--wait=watcher` forms appear; and how much the file checks separate the arms given the style reference.
