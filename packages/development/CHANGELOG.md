### Added

- the local CI gate report says when a failure may be staleness (kata `w6tn`). The gate grades the PR head while hosted CI grades the merge ref, so a head based before the last main release can fail here (the pi version-bump hook in `generate:pi`, then generated drift) while hosted CI passes. When a `run` or `gate` fails and `git merge-base --is-ancestor <base> <head>` says the head lacks the base, the report gains `notes: [{kind: 'head-behind-base', behind: N, baseRef, message}]` telling the operator to update the branch and re-run before treating it as a defect. Advisory only: `ok`, `mergeReady`, `failures` and the posted status are unchanged, nothing is added on a pass or when the head contains the base, and a git error means no note. Documented in `skills/local-ci-gate` (SKILL.md, RUNBOOK.md); grading the merge ref or refusing stale heads is deliberately not done.
- the local CI gate reuses hosted CI results for the same head instead of re-running them (kata `fwj0`, landed by kata `ehsm`; PRD-2026-4dec59b8 REQ-019, TRD-015). Before, `gate` re-ran in a clean clone, under Node 22 and 24, the `validate`, `test (22)`, `test (24)` and generated-drift jobs that hosted CI had already passed on the same head (on PR 245 all 15 hosted checks were green and the merge still waited for the local status). A repository opts in with a `hosted_reuse` block (`covers`, `extra_workflows`) in the base-ref `.ensemble/local-ci.yaml`; absent, nothing changes, and every name in `steps` must be listed in `covers`, so a step added without a hosted counterpart switches reuse off. `merge` then accepts, and `gate` returns without taking the gate lock, cloning, running or posting, when GitHub Actions itself recorded every required job as completed with conclusion `success` on the exact head SHA. The CLI reads `actions/runs?head_sha=` and each run's jobs from GitHub (the jobs are never taken from check runs, commit statuses or the payload); the required job names are derived from the base-ref config and the base-ref workflow files; each required workflow file must be the same git blob at the PR head and at the base ref (hosted CI ran the head's own copy); only runs bound to this PR count (its number and base branch in `pull_requests`: a fork PR never gets hosted acceptance, and `base.sha` is not compared because `dev` moves constantly); the latest run per workflow and event counts, a `pull_request` run is required, and the listings must be complete (integer run ids, integer `total_count`). The jobs must also have done the work: every job in a required job's `needs:` closure must have concluded `success` in the same run, and every step of each required job must have concluded `success` (steps are mapped positionally to the base workflow's; a skipped step is accepted only where the base step's `if:` is a pure matrix comparison, like `Upload coverage` on `test (22)`; GitHub's own set-up, complete and post steps are exempt). That step check is the real guard; repo-local actions or reusable workflows, `continue-on-error` other than `false` and an `if:` matching `github\.(head_ref|actor|triggering_actor|event)\b` (so `github.event` and every `github.event.<anything>` are refused, `github.event_name` is not) in a required job or its `needs:` closure are refused earlier as a static blacklist, not a proof. A recorded local run vetoes hosted acceptance, and the veto is written ahead: the gate posts `pending` in the configured context on the head BEFORE a local run and refuses to run when it cannot, so a crash, a kill, a timeout, a thrown runner, an unpostable final status or a transient refusal leaves the latest status `pending`, and every head-bound refusal (a failed or unsupported step, a tampered clone, unexpected output, an unreadable workflow, a moved clone, a runner error) publishes a `failure`. `merge` and `gate` both read the head's statuses from GitHub themselves (the caller's `statuses` payload no longer decides) and the first, newest, status in the configured context decides: only a `success` whose record verifies for the head (`verifyRecord`: the commit, the trusted config blob and the workflow set; it does not bind who posted it) clears; `pending`, `failure`, `error`, an unverified success, and an unreadable, malformed or full-page list veto; no status at all vetoes nothing. The context is the `status_context` of the base config (`ensemble/local-ci` everywhere surveyed). `merge` then refuses (re-run the gate with `forceLocal:true`) and `gate` runs locally; any passing local `gate` run clears a veto, because it posts the verified `success` (a non-forced `gate` whose hosted check is vetoed falls through to the local run; `forceLocal:true` only skips the hosted check). The local route of `merge` applies the same latest-wins rule and, when GitHub lists nothing in the context, judges a non-success payload status on the head or without a usable SHA by the same rule as the hosted route. The PR head's own steps run as the maintainer and could post a verifying status with the maintainer's credential, so the runner now isolates them: each run gives a step a scratch `HOME`, `GH_CONFIG_DIR`, `XDG_*` and `TMPDIR`, null git global and system config, none of the inherited tokens (`GH_TOKEN`, `GITHUB_TOKEN`, `NPM_TOKEN`, `SSH_AUTH_SOCK` and the like) and a `gh` stub ahead of the maintainer's `PATH` (a bare `gh` in a step exits 127), and after the last step, before the final status is posted, kills every step's process group and every process of the user whose environment carries the run's marker (`leftoverProcessesKilled`). This is not a sandbox: head code runs as the same OS user, so the real credential files by absolute path or through `os.userInfo().homedir`, the macOS keychain, a child that scrubs its environment and leaves the process group, and a workflow with `statuses: write` stay open, and `sandbox-exec`, `bwrap`/`unshare`, another OS user or container, or a status-posting identity the steps cannot reach are not done; `verifyRecord` does not bind the creator and the local success route has the same property, so hosted reuse is no weaker than what the gate already trusts. The runner no longer throws over a result when a step leaves unreadable directories: permissions are repaired, and a clone that cannot be removed is a head-bound `runner-error`. The untracked-file check fails closed too: a directory a step made unreadable (git lists nothing in it and still exits 0) makes the run `clone-tampered`, so planted files cannot hide there. After hosted verification `merge` and `gate` re-read the PR and refuse if it is no longer open or its head changed (`gate` stops at stage `config`). A red, cancelled, skipped, running or missing job, a job on another commit, an edited workflow file, a truncated listing, a repo that is not `owner/name`, a config that does not opt in or an unreadable answer is refused: `gate` then runs locally under the gate lock and reports `hostedRefused`; `merge` refuses with the hosted reason beside the local one; `forceLocal:true` skips the shortcut. A verified local status still wins in `merge`. The review precheck now says its detached gate posts the status when it finishes unless hosted CI already verified the head, in which case it runs nothing, posts nothing and its log says `stage hosted`, and that a `pending` status no run is working on needs `forceLocal:true`. `pr-merge.yaml` 2.4.2 words its never-merge rule 'a verified pass bound to the exact head SHA (local status or verified hosted jobs)'; the human `CHANGES_REQUESTED` refusal, the review gate and the approvals are untouched. This repository opts in in `.ensemble/local-ci.yaml` with two declared fidelity gaps (hosted `validate` and `drift` run on Node 24 only; `generate-validate` is declared covered by `npm run generate`; delete a name from `covers` to refuse reuse), and a PR is graded by its base-ref config, so reuse applies only after this change is on the base branch. Rollout order: a gate CLI older than this change rejects the unknown config key `hosted_reuse` and refuses every PR once the key reaches `dev`, so release and update clients first and merge the config block after (this change adds both together); the gate now needs permission to post commit statuses before the run as well as after it. Remove `hosted_reuse`, or always pass `forceLocal:true`, before making `ensemble/local-ci` a required check, because a head accepted through hosted jobs never gets that status. Not verified: who triggered a hosted run; that its steps are honest beyond the workflow file matching the base; that the merge commit a `pull_request` run tested (head plus the base tip at run time) is the base tip as it is now; that external actions (`owner/repo@tag`) are unchanged since review; steps inside composite actions (the API does not list them); that the verified SHA is the one merged, because it is not passed to the merge step (`--match-head-commit`: `pr-merge.yaml` is at 2499 of its 2500-word ceiling); the window between the statuses read and the merge; a status writer with the gate's credentials, or the PR head's own steps within the limits above, can post a verifying success and so clear a veto; a dry run, or the `run` command, records nothing and vetoes nothing; and a veto is bound to a head SHA, so a new commit is a new head graded by hosted CI unless the gate runs on it. No branch protection is read or changed. Sensitive paths: `local-ci-cli.js` (`merge`, `gate`), `local-ci-runner.js`, `local-ci-hosted.js` (new), `local-ci-config.js`, `.ensemble/local-ci.yaml`, `pr-merge.yaml`.

So a dispatcher on it passes `effort` and `model` (what it asked for) and its own `retries`, and `tool_calls`, `turns` and `rate_limits` are `null` with that reason in `timing`: this change names the gap, it does not close it. The slice sizes, per-reviewer finding counts and per-round vote tallies of `summary.json` are NOT added: their producer is the measurement driver, which is not in the repository. - a re-review is a delta, not a full re-read, when the first round lost a verifier, and the delta verifies what that verifier left unverified (kata `p5dt`, epic `5e1t`, from the final-code measurement, kata `q3a9`, epic `ptqb`: the High re-review of scratch PR 286 was `prior-round-unusable:state-round-incomplete`, a full read by 8 agents in 16.5 minutes against a plan of 10 to 15 with 0 carried, because 3 of the first round's 12 verifiers had expired at their 5-minute deadline, although that round had read every path, its security lane was clean and no reviewer was lost; 8 of 31 verifiers expired across the three runs, so a delta was reachable only when none did). A verifier that never returns leaves no path unread: the candidates it held stand in the ledger `unverified` / `verifier-incomplete` (presented, never confirmed, never refuted). `review-run` now takes such a round as a delta base when its state accounts for the loss: `notReviewed.expiredAgents` lists only verifiers, each named in `incompleteVerifiers` with the candidates it held, and each of those candidates is unverified for want of a verifier in the ledger. A lost reviewer or security lane, an unreviewed slice or path, a path read under too few lenses, an unbriefable candidate, a result that changed after it was read and a state that does not add up are still `state-round-incomplete`, a full re-read. The delta round then puts the last round's unverified candidates to verifiers again, sorted by the fixed-finding check that already clears prior findings (`deriveCleared`, git): one the push fixed is cleared (never verified, never counted refuted), one a reviewer of this round raised again is verified as that candidate and replaces the old entry, one whose cited lines the push left alone comes back as a candidate of this round under its own id (its entry as recorded, at the line this head numbers it) and K fresh verifiers are asked about it (the votes that did arrive last round are not counted again: they were cast on another head), and any other (a renamed file, a place the check cannot give, a check that cannot run, an entry with no raiser) is not verified again: it stays in the ledger as recorded, unverified, and the round says so. Nothing is dropped and nothing is counted refuted for want of a vote. - `pr-review-explainer` skill and the High-tier offer (REQ-022). The skill produces a short explainer for a named module from the code as it is now, naming every file it read, so a reviewer coming to an unfamiliar area gets context that is traceable rather than remembered. `lib/pr-review-explainer-offer.js` decides when one is offered: a High-tier PR's review report offers an explainer for each touched sensitive module, a PR below High offers none, and an explainer is generated only when it is requested.
- Cross-runtime reachability and no-new-secrets proof (REQ-023, REQ-024). `lib/pr-review-reachability.js`, reached as the `reachability` subcommand (`trace`, `runtimes`, `secrets`), grades three claims that are easy to assert and easy to get wrong. `trace` holds a chain end to end -- entry command text -> skill -> a subcommand the CLI really registers -- so prose that merely *names* a subcommand is not a call, and an entry point reaching past the skill into the CLI is reported as a boundary violation rather than counted as reachability. `runtimes` grades Claude, Pi, Codex and OpenCode against a baseline and states any reduction in words, because the requirement permits a reduction only if the report says what it is. `secrets` names new CI secrets and finds a credential surviving anywhere in a lib's output, nested values and object keys alike; an empty secret is refused rather than matching nothing and reading as "clean". **The measured result for this repository:** Pi is equivalent to Claude -- same procedures, same subcommands, and the same payloads produce byte-identical output from each runtime's own shipped CLI -- while Codex and OpenCode are **reduced**: both generate the command entry points, but neither bundles the `pr-review-*` procedure skills or a vendored CLI, so the graded steps do not run there. - `pr-review-sweep` skill: an on-demand review of code that is already merged (REQ-021). It reports: no edit, no commit, no push, no PR. - Review depth modes for `pr-review-cycle`. The risk tier selects the mode and `pr-review-cli.js depth` grades the planned (and the used) reviewer and verifier counts against its bounds: **Quick** a single reviewer and no verifiers, **Standard** at least two reviewers and 3 verifiers, **Deep** at least two reviewers and 5 verifiers. - Verification before posting, with published vote thresholds. Every candidate finding -- from every reviewer, every local tool and every review bot, CodeRabbit included -- enters the same ledger and is voted on by fresh-context verifiers that did not raise it (`pr-review-cli.js votes`). A finding is presented only on a **strict majority of the verifiers the depth expects: 2 of 3 at Standard, 3 of 5 at Deep**; the denominator is the expected count, never the votes that arrived, so a missing verifier is never read as agreement. A rejected finding reads "verifier disagrees" and keeps its tally in the ledger, a critical or security-relevant finding the verifiers split on or reject is `disputed` for a person to decide, an incompletely verified one is presented as `unverified`, and a runtime with no subagent capability runs a single-pass review whose report and state report both carry the reduced-review notice -- a reduced review is never reported as a verified one.

### Changed

- **BREAKING, packages/development:** a resolution that closes a blocking finding now carries a typed `decision`, and only `accept` closes one (kata `785h`). Before, the merge gate took any resolution with `reason`, `by`, `at` and `headSha` as closing an Important, security or unrecognised-severity finding, whatever the reason said: a `reason` of "Fix on this PR" made `evaluateGate` answer `mergeable:true` with no fix, and only the skill's prose forbade it. A resolution now needs `decision`, exactly `accept` or `follow-on` (`RESOLUTION_DECISIONS`, exported from `lib/pr-review-ledger.js`). `accept` closes a blocking finding (Important, Critical, unrecognised severity, a security-lane entry, a coverage gap); `follow-on` is valid only for a Nit or Pre-existing finding, because a follow-on PR cannot unblock the gate. `resolutionProvenanceProblem`, the one check the gate, the disposition list, coverage-gap closure and `recordOperatorResolution` share (it derives the finding's class with `closesBlockingFinding`), ignores any other resolution, so a hand-written resolution without a valid `decision`, or with `follow-on` on a blocking finding, leaves the blocker open and carrying `resolutionRejected`. `ledger resolve` refuses a missing or other `decision` (`fix-here`, `ACCEPT`, a non-string; a fix answer is named a `FIX_SELECTION`) and refuses `follow-on` on a blocking finding; it takes an optional `lane: true` for a security-lane entry. `recordResolution` refuses a `decision` that is present and invalid. The run's status counts (`pr-review-run.js`) now read each prior finding as the gate does (`withoutRefusedResolution`), so a resolution the gate would not honour no longer lets the local phase read `LOCAL_REVIEW_COMPLETE`; the CLI `ledger isActionable` action and skill Step 4 keep the ledger's raw reading, which the docs now say is not the authority (follow-up: kata `rsja`). Resolutions already recorded without `decision` stop counting and must be re-recorded (they are head-bound anyway). Honest limit: a session can still type `accept`; the field makes the closing choice explicit and refuses a fix answer, it does not authenticate the operator.

- BDD/Reqnroll stays on by default in `/ensemble:create-trd` and `/ensemble:implement-trd-beads`, and a repo that does not use it can now opt out. Both commands resolve one `BDD_MODE` through the new `trd-cli resolve-bdd` (`lib/bdd-mode.js`); first match wins: `--bdd` / `--no-bdd` (`create-trd` only), the `ENSEMBLE_BDD` environment variable, the TRD's `test_approach` frontmatter (`bdd-reqnroll` or `standard`, written by `create-trd` only for an explicit choice, so `implement-trd-beads` honours an opt-out without the environment variable), otherwise on. With BDD on (the default) nothing changes: >=3 scenarios per functional REQ, and `-TEST` beads go through `reqnroll-cli`, RED confirmation and `reqnroll-binding-specialist`. With BDD off the `-TEST` pairing and one `Test AC:` item per AC-NNN-M stay, the >=3 floor becomes a readiness-scorecard note that never blocks or lowers the score, and `-TEST` beads are implemented in the repo's own test framework and run through `test-runner.run`. A repo with no Reqnroll, such as BT3, opts out once with `ENSEMBLE_BDD=0` (or `--no-bdd`). The `create-trd` step "Test Task Generation (BDD)" is now "Test Task Generation". Foreman table mode (`--parser-tables`) is unaffected. See `README.md#optional-bdd-reqnroll`.
- `trd-cli resolve-bdd` reports what it finds whichever source decides: an unrecognised `ENSEMBLE_BDD` or `test_approach` is ignored with a `Warning:` line in `message` (one line per warning), even when a flag, the environment or the TRD stamp wins. The stamp is read wherever the frontmatter sits: line 1, or under an H1 or an HTML comment. `--trd` is an explicit request, so a relative path is read as given and then from the repo root, and a file that cannot be read, or `--trd` with no path, is an `{error}` with exit 1 that the commands HALT on rather than a silent default.
- `trd-parser.js` exports `scanFrontmatter` (moved from `trd-cli.js`, unchanged), the frontmatter reader that accepts an H1 or HTML comment above the `---` block; `bdd-mode.js` uses it to read `test_approach`.
- The merge gate narrows what closes an Important, unrecognised-severity or security-lane finding. A recorded `resolution` closes it only if it carries a `reason`, the deciding login (`by`), an ISO-8601 timestamp with a zone (`at`) and the `headSha` it was decided against, equal to the gate's head. Handed the policy (`gate` and `ledger resolve` take `policy`, the block `approvals` takes), `by` must also not be one of its `botLogins` and, when it names `maintainerLogins`, must be one of them. Every security-lane `resolution` needs this, a Pre-existing lane entry included. The review's own deferral of a non-blocking Major (`blocking: false`, deferred, a `reason`: the stopping rule) no longer closes an Important finding at the gate, so it stays open until it is fixed or the operator records a decision (a deferred legacy Critical now blocks too). A refused closure leaves the finding blocking and its blocker carries `resolutionRejected` or `deferralRejected`. A push makes earlier decisions stale. **What this does not do:** it proves a reason, a login and a head binding, not that a human typed them, so a session that writes a permitted login into `by` passes, and without `policy` the login is checked for shape only. `cleared: true` is still taken at its word, and `isActionable`, the review cycle's own question, still reads the deferral. `pr-review-cli.js gate` now also carries the decision list next to the unchanged verdict.

The operator's way out is the existing one and nothing new: run the review again on this head, or `ledger resolve` the gap (the decision list shows it in its own `Not reviewed` group with Accept as its only choice, worded for what happened to the gap), graded by the same provenance rule as a finding's decision and reported as `coverage-gap-accepted`. `review-run` builds the record from the stored run and feeds the gate, the status and the decision list from it; `carry` `action: 'coverage'` carries every gap of the earlier report through a delta round and none through a full range. The security lane keeps its own mechanism and a reader the plan never made (`reader-not-planned`) stays a reported limit, not a gap. One operator action: `coverage` is now a required input, so a state report written before this release has none and `status` and `gate` read it as `review-data-unavailable` / `LOCAL_REVIEW_BLOCKED` until a FULL-range round of that PR writes it: `carry` `action: 'coverage'` answers a delta round over such a report `unavailable` with `fullRangeRequired: true` (so does every delta round after it), so re-run the round once over the full range (`deltaPlan.mode: 'full'`). Limits, stated: the beads recorder records one bead per open gap but the runner never calls it, so a light-mode run's coverage gaps get no bead (the decision list still shows each one); an empty diff has no coverage to grade and is refused as unavailable data (an owner decision whether it should read as complete).
- The PR-review beads recorder binds its checkout to the pull request's repository (kata `97ra`, epic `ptqb`). `pr-review-beads-cli.js` took `repoRoot` on trust: a `repoRoot` that was another repository (a fork checkout, or any unrelated repository) received the beads of a pull request that is not its own. `checkTrust` now starts by finding the primary checkout and requiring that its `origin`, every fetch and push URL, names `repo` (case-insensitive; https, ssh and scp-like forms), before the host or the tracker is asked: another repository is `REFUSED` `repository-mismatch`; no `origin`, a URL that names no `owner/name` or a git that cannot list the remotes is `repository-unknown`; a repository with no primary checkout is `no-primary-worktree` (a linked worktree's own remote configuration is never consulted, and a fork checkout whose `upstream` names the repository is still refused). The binding (`bindRepository` in `pr-review-repo.js`) is the one the merge sweep made in `local-ci-sweep-record.js`, which now gets it from `checkTrust` instead of carrying its own copy; its behaviour is unchanged.
- Toolchain runner: a non-zero exit with an empty stderr now reports the tool's own JSON error envelope from stdout in the `TOOL_FAILED` message (kata `6z28`). `br` prints `{error:{code,message,hint}}` on stdout and exits non-zero, so `toolchain-cli run tracker.list` outside a beads workspace used to say only "Command failed: br list ..." and never `NOT_INITIALIZED`. Non-empty stderr still wins, stdout that is not an error envelope still falls back to Node's message, and the detail is redacted and length-bounded like stderr, for both `runCapability` and `runCapabilitySync`. Every string leaf of the envelope is redacted before it is serialized, so a double-quoted value such as `password="..."` (whose quotes JSON escapes to `\"`, defeating the key-value pattern) no longer leaks; the zero-exit stdout-envelope path shares that helper.
- `adapter-tracker-beads`: `tracker.create` and `tracker.dep-add`/`tracker.dep-remove` could not parse a real `br` response. Their output shapes had been inferred from `br schema commands` rather than captured, and the inference was wrong: `br create --json` prints a bare issue object (the adapter indexed `$[0]` and failed `BAD_OUTPUT: mapOutput: path '$[0]' indexes '[0]' into a non-array value` after the bead had already been created), and `br dep add/remove --json` prints `{status, issue_id, depends_on_id, type, action}` with no `id`. Both now parse the captured shapes; the stubs in `scripts/tests/` (`adapter-tracker-beads-stub.js`, `tracker-swap-scenario.test.js`) emitted the same wrong shapes and were corrected, which is why the existing suites never saw it. `SKILL.md` also records that `tracker.update` replaces notes rather than appending (unchanged; `refine-beads` uses it as shipped).
- `trd-cli.js` no longer truncates its JSON when stdout is a pipe. The CLI wrapper ended in `process.exit(code)`, but Node writes a pipe asynchronously, so everything past the 64 KiB (65536-byte) pipe buffer was still in flight when the process was killed: `node lib/trd-cli.js parse <large TRD> | consumer` handed the consumer invalid JSON cut at exactly position 65536, while the same command redirected to a file produced the complete object. Repository TRDs parse to ~84 KB, so any pipe consumer of `parse` or `scaffold-plan` on a large TRD was broken. The wrapper now sets `process.exitCode` and lets the event loop drain stdout, so piping and redirecting are byte-identical; exit codes are unchanged (0 on success, 1 on failure). `tests/trd-cli-flush.test.js` runs the real binary through a real pipe with a fixture whose output exceeds the buffer, plus a guard assertion that keeps the fixture from silently shrinking below it.
- `pr-review-cli.js` redacts credential-shaped values in everything it prints. Redaction was applied only before a review-state report touched disk, so a token that appeared in a finding's text survived into the CLI's stdout — the exact text that becomes a ledger entry or a PR comment — through `ledger` and `votes`. It is now applied at the single output boundary in `main()`, covering the error path too (a refusal echoes the payload that caused it) and any subcommand added later without anyone remembering to ask. Found by running the shipped binary rather than calling the libs in process, which is why the existing in-process suite passed: `normalizeFinding` does redact. The same fix was re-vendored into `packages/pi/vendor/`, which had drifted and was still printing the credential, so the same review was clean on Claude and leaking on Pi.
- `trd-parser.js` now accepts `Implementation AC checklist:` / `Test AC checklist:` labels. `create-trd` instructs authors to write that form, but the parser matched only `Implementation AC:` / `Test AC:`, so every acceptance criterion in a TRD written as instructed parsed as empty and `implement-trd-beads` could not scope task bodies.
- `ensemble-new-feature` now reads its invocation from `$ARGUMENTS`. The pi prompt contained no argument placeholder, and pi substitutes arguments only where one appears, so `/ensemble-new-feature --foreman <idea>` silently dropped both the flag and the idea.
- Runner subagent dispatches now resolve. `beads-build.yaml` dispatched `Task(subagent_type=beads-build-wave)` and `implement-trd.yaml` dispatched `Task(subagent_type=implement-trd-task)`, but both targets shipped only as commands, never as agents — so neither dispatch could resolve and `/ensemble:beads-build`'s Execute phase and `/ensemble:implement-trd`'s Task Loop were both unreachable. Added thin runner agents that load their command as the single source of truth rather than duplicating the procedure.

### Added

- `implement-trd-beads` v2.2.0: team-based execution model with role-based handoffs
  - `team:` YAML section: optional top-level configuration for role-based execution (lead, builder, reviewer, qa roles)
  - Per-task state machine: sub-state tracking via br comments (in_progress/in_review/in_qa/closed)
  - Lead orchestration loop: tech-lead-orchestrator drives task assignment, reviewer/QA delegation

  - Optional skip gating: lead can skip review and/or QA per task with audit trail
  - Cross-session resume: team sub-states reconstructed from br comments on resume
  - Team metrics: per-phase performance summary (builder pass rates, cycle times, rejection counts)
  - Wheel instructions: team-aware output with topology, lifecycle diagram, NTM spawn commands
